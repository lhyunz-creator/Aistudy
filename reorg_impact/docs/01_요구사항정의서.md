# 01. 요구사항 정의서

> 조직개편 권한 룰 영향도 분석 도구
> 이 문서만으로 프로젝트 전체를 이해할 수 있도록 작성되었다.

---

## 1. 배경

사내 IAM 포털은 권한별로 **자동화룰**과 **통제룰**을 운영한다. 두 룰 모두 부서 조건을 **조직코드 기준**으로 저장한다.

조직개편으로 조직코드 체계가 바뀌면 두 가지 문제가 생긴다.

1. **룰이 조용히 고장난다** — 없어진 조직코드를 가리키는 룰은 아무에게도 걸리지 않는다. 에러도 안 나고 로그도 안 남는다.
2. **대상자가 조용히 바뀐다** — 룰을 한 글자도 안 고쳤는데, 조직 트리가 바뀌어 `하위부서 포함` 룰의 적용 인원이 대폭 달라진다.

둘 다 **아무 신호 없이 발생**한다는 게 핵심이다. 그래서 개편 때마다 수작업으로 전수 점검해야 하는데, 룰 수가 많아 현실적으로 누락이 생긴다.

## 2. 목적

개편 전후 데이터를 비교해 **영향받는 룰을 빠짐없이 찾아내고, 조치 판단에 필요한 근거를 제시**한다.

## 3. 범위

### 하는 것
- 조직코드 변경 유형 자동 분류
- 영향받는 룰 식별 및 영향 인원 산출
- 검토용 리포트 생성
- 검토자의 조치 결정 수집

### 하지 않는 것
- 권한 판정 로직 자체 (이미 운영 중, 변경 대상 아님)
- **룰의 실제 DB 반영** — 이 도구는 변경 제안서까지만 만든다
- 일일 배치 회수 로직 (기존 운영 로직)
- 운영 DB 직접 접근 — 입력은 CSV, 출력은 파일

## 4. 기존 IAM 룰 구조 (전제, 변경 금지)

### 4.1 룰의 두 종류

| 종류 | 동작 |
|---|---|
| 자동화룰 (AUTO) | 조건 충족 시 신청 없이 권한 자동 부여 |
| 통제룰 (BLOCK) | 조건 충족 시 해당 권한의 **신청 페이지 접근 차단**. 이미 보유한 권한을 회수하지는 않음 |

두 룰은 **완전히 독립**이다. 같은 사람이 같은 권한에 대해 AUTO와 BLOCK에 동시에 걸릴 수 있고, 그 경우 자동 부여는 그대로 진행되며 신청 페이지만 막힌다.

### 4.2 룰 내부 조건

```
룰 = 권한 + 부서조건(1개 이상) + 직무조건(0개 이상)

부서조건끼리        → OR
부서조건 ↔ 직무조건 → AND
직무조건이 비어 있으면 → 직무 무관, 부서조건만으로 판정
```

### 4.3 부서 매칭

각 부서조건에는 **하위부서 포함** 여부가 붙는다.

| 설정 | 대상 |
|---|---|
| 미포함 | 해당 조직 **직속 인원만** |
| 포함 | 해당 조직 + **트리 말단까지 전체 하위 조직** (깊이 제한 없음) |

### 4.4 룰 간 관계
- 한 권한에 여러 룰이 붙을 수 있다
- **룰끼리는 서로 독립**이다. 우선순위나 상쇄 관계가 없다
- AUTO 룰 중 하나라도 매칭되면 부여 대상. 중복 매칭돼도 권한은 1회만 부여

### 4.5 재평가
매일 **14:00 배치**로 전체 재평가한다. 자동 부여 상태이나 현재 어떤 AUTO 룰에도 매칭되지 않는 사용자는 권한이 회수된다.

## 5. 용어

| 용어 | 정의 |
|---|---|
| 조직코드 (orgCode) | 조직 식별자. **모든 판정의 기준 키** |
| 상위조직코드 (parentCode) | 조직 트리의 부모 노드 |
| 조직명 (orgName) | **판정에 사용 금지.** 리포트 표시용으로만 사용 |
| 조직개편 발령 | 조직 구조 변경에 따른 일괄 이동 |
| 전배 발령 | 개인 단위 인사이동. **판정에서 제외** |
| 고아 룰 | 개편 후 존재하지 않는 조직코드를 참조하는 룰 |
| 범위확대 | 룰은 그대로인데 대상 인원이 늘거나 주는 현상 |

### 왜 조직명을 쓰지 않는가
룰이 코드 기준으로 저장되므로, 이름이 바뀌어도 룰에는 아무 영향이 없다. 이름을 판정에 섞으면 "이름만 바뀐 조직"이 변경 건으로 잡혀 검토 대상이 불필요하게 늘어난다. 반대로 "이름은 그대로인데 코드가 바뀐" 진짜 위험한 케이스를 놓칠 수도 있다.

---

## 6. 입력 데이터

CSV 6종을 수동 업로드한다. **전부 UTF-8.** (상세는 03 데이터딕셔너리)

| 파일 | 내용 |
|---|---|
| orgs_before | 개편 전 조직 목록 |
| orgs_after | 개편 후 조직 목록 |
| members_before | 개편 전 임직원 목록 |
| members_after | 개편 후 임직원 목록 |
| assignments | 발령 내역 (조직개편/전배 구분 포함) |
| rules | 현재 권한 룰 목록 |

> **룰 목록이 반드시 필요하다.** 조직 데이터만으로는 "조직이 어떻게 바뀌었나"까지만 알 수 있고, "그래서 어느 룰이 영향받나"는 계산할 수 없다.

## 7. 처리 흐름

```
Step 0  입력 로드 · 인코딩 검증 · 필수 컬럼 검증
Step 1  조직 트리 구성 (before / after 각각, 말단까지 전개)
Step 2  발령 필터링 — 조직개편 건만 추출, 전배 제외
Step 3  조직코드 변경 유형 분류 (→ 02 문서)
Step 4  룰 영향도 분석
Step 5  대상자 시뮬레이션 (before vs after)
Step 6  리포트 생성
```

### Step 2 — 발령 필터링
- 발령사유코드가 **조직개편 구분값인 건만** 사용한다
- 전배 발령은 인원 이동 비율 계산에서 **전량 제외**한다
- 전배가 섞이면 비율이 오염되어 변경 유형 판정이 전부 틀어진다
- 동일 사번이 복수 발령된 경우 발령일자 최신 건 기준
- 개편 기준일 ±N일(설정값) 범위 건만 개편성으로 인정

### Step 4 — 룰 영향도 분석

**4-1. 고아 룰 검출 (최종 안전망, 반드시 수행)**

전체 룰을 스캔해 조직코드가 개편 후 조직 목록에 없는 룰을 전부 추출한다.

| 코드 | 의미 |
|---|---|
| OR-01 | 개편 후 조직에 없는 코드 참조 |
| OR-02 | 짝짓기 실패로 조치 없이 방치된 룰 |

이 건수를 **리포트 최상단에 표시**한다. 분류 로직이 무엇을 놓치든 이 검사에는 걸린다.

**4-2. 범위확대 경고**

룰은 변경되지 않지만 대상자가 달라지는 케이스. 룰별로 산출한다.
- 자동화룰 → 신규 부여 예정 인원 / 권한 상실 예정 인원
- 통제룰 → 신규 차단 예정 인원 / 차단 해제 예정 인원

**4-3. 충돌 룰 검출**

조직 통합 시, 동일 권한에 대해 서로 다른 종류(AUTO/BLOCK)의 룰이 함께 딸려오는 경우를 추출한다. 기계적 판단이 불가하므로 **결정하지 말고 검토 대상으로만 제시**한다.

**4-4. 중복 룰 검출**

동일 권한 + 동일 종류 + 동일 직무 조합의 룰이 복수 존재하면 병합 후보로 표기한다.

### Step 5 — 대상자 시뮬레이션

기존 판정 로직(4장)을 그대로 재현해 개편 전/후 대상자 명단을 각각 산출하고 차집합을 낸다.

```
before_targets = 개편 전 트리 + 개편 전 임직원 기준 매칭 결과
after_targets  = 개편 후 트리 + 개편 후 임직원 기준 매칭 결과

신규 대상자 = after - before
이탈 대상자 = before - after
```

## 8. 출력물

| 파일 | 내용 |
|---|---|
| org_changes.csv | 조직 변경 분류 전체 |
| rule_actions.csv | 룰별 조치 제안 및 결정 |
| member_impact.csv | 룰별 영향 인원 |
| summary.md | 사람이 읽는 요약 |

출력 CSV는 **UTF-8 with BOM** (Excel 한글 깨짐 방지).

## 9. 원칙

- **읽기 전용** — 운영 DB에 접근하지 않는다
- **결정론적** — 같은 입력이면 항상 같은 결과
- **조용한 실패 금지** — 스킵·경고는 사유와 함께 전부 로그에 남긴다
- **부분 실패 허용** — 개별 건 실패 시 해당 건만 판정불가 처리하고 전체는 계속 진행
- **추측 금지** — 정의되지 않은 동작은 `TODO: 정의 필요`로 표시하고 임의 구현하지 않는다
- **근거 동반** — 모든 판정 결과에 판단 근거 값을 함께 반환한다
